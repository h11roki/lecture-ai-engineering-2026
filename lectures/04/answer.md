#### コードで判定する基準と、LLM に任せる基準の使い分け

- コードに向くのは、判定の定義を 1 文で書けて、言い換えで結果が変わらないもの
  - 回の表示（末尾に「第N回」がある）
  - 承認待ちで止まったか。回答の文ではなく、エージェントの出力が `DeferredToolRequests` かどうかで決まる
  - 確認問題の答えを明かしていないか。`make_quiz` が返した答えの文字列が回答に含まれるかで見られる
- LLM に任せるのは、意味の判断が要るもの
  - 根拠：矛盾しているか、断定しているか
  - 範囲：講座の範囲か、断っているか
  - ヒント：完成した答えか、ヒントか
  - 分かりやすさ
- ただし、コードも「何を測るか」を人が決めた範囲でしか正しくない
  - 実装の #07 では、「最後の行に含む」が、1 行の JSON の本文の中の「第2回」を拾って見逃した
  - 演習の #07（関係する回：なし）・#09（空の質問への案内）のように、回を示しようがない回答も落とす
  - コードの判定も LLM と同じく、人のラベルと比べて、定義が合っているかを確かめる必要がある
- LLM は、ある基準の理由を別の基準に持ち込む（実装の #10 ヒント、演習の #06・#08 根拠）。LLM に任せる基準には、何を見るかだけでなく、何を見ないかまで書く必要がある（基礎の rubric の文言で直った）
- 中間にあるもの（例：「用語集に無い数字を出していないか」）は、まずコードで候補を拾う（回答の数字が参照の定義に無い）。そのうえで、LLM か人が確かめるのがよいと思う

#### 作った人数と手順

1. 元の SWE-bench（2023 年）：人は問題を作っていない。12 個の Python リポジトリから約 9 万件の PR を集め、「マージ済みで、issue を解決し、テストを足している」もので絞り、実際に環境を作ってテストを走らせて「修正前に落ち、修正後に通るテストがある」ものを残した（2,294 件）。問題文は、issue を書いた元の開発者のもの
2. SWE-bench Verified（OpenAI、2024 年 8 月）：元の 2,294 件から無作為に選んだ 1,699 件を、Python の経験がある開発者 93 人で分担して注釈した。1 件を 3 人が独立に見ている（注釈は計 5,097 件）
   - 聞いたこと（注釈の手引き）
     - issue の明確さ（0〜3）：issue の本文だけ（下の議論は読まない）で、正しい解がどんなものか分かるか
     - テストの妥当さ（0〜3）：テストが正しい解をすべて通すか。元の PR で足した関数名やエラー文に依存して、別の正しい解を落とさないか
     - 難易度（15 分未満〜4 時間超）、その他の重大な問題の有無、自信（1〜5）
   - 落とす規則：3 人のうち最も厳しい評価を採り、issue の明確さかテストの妥当さが 2 以上、またはその他の問題があれば落とす。公開された注釈データの 1,699 件すべてが、この規則どおりだった
   - 結果：1,160 件（68.3%）を落とし、539 件が残った。落とした理由（重なりあり）は、issue が不明確 650 件（38.3%）、テストが正しい解を落としうる 1,039 件（61.2%）、その他 135 件（7.9%）。Verified の 500 件はすべて、残った 539 件に含まれる。539 件から 500 件をどう選んだかは、ブログを読めず確かめられなかった

#### 気づき・疑問

- どちらも「採点を信じてよいか」を人が確かめている点は同じだが、確かめる場所が違う。SWE-bench Verified は採点（テスト）が決定的な代わりに、テストが正しい解を落とさないかを 3 人ずつ見ている。今日の演習は採点（LLM）が揺れるので、人のラベルとの一致率で確かめた
- 専門の開発者でも、3 人の評価が完全にそろうのは 3 割ほどしかない。1 人のラベル（今日の 10 件）だけで「採点器を信じてよい」と言うのは危うい。Verified は割れたときに厳しい側を採り、問題の質と引き換えに件数を 1,699 件から 539 件まで減らしている
- 読んだ 4 件のうち 2 件（sympy、sphinx）は、テストが issue に書かれていないこと（足し算の結果、ID の文字列）まで見ていた。それでも 3 人とも「正しい解はすべて通る（0）」と付けていた。注釈者は元の PR の修正（正解のパッチ）を見ながら判断するので、そのやり方に引っ張られたのかもしれない。演習で講師のラベルを先に読んでから自分のラベルを付けたのと同じ形の偏りだと思う
- django__django-11099 の FAIL_TO_PASS には、issue と関係のない別のクラスのテスト（`test_help_text`）も入っていた。なぜ入っているかは確かめていない
